# Requirement-to-evidence map

SA04 is partial. This page accounts for the client clauses in the final
[FAPI 2.0 Security Profile](https://openid.net/specs/fapi-security-profile-2_0-final.html),
including relevant network and cryptography clauses. The companion maps cover
the supported OIDC/OAuth paths and JWT/Message Signing duties:

| Map | Coverage and remaining boundary |
| --- | --- |
| [OIDC](requirements-oidc.md) | Discovery, authorization code, all 13 ID-token validation steps, UserInfo and refresh; optional features and deployment duties are named separately. |
| [OAuth](requirements-oauth.md) | Code/refresh, client authentication, bearer transport, S256, metadata and callback issuer; related extensions have their own scoped maps below. |
| [OAuth security (partial)](requirements-security.md) | RFC 9700 sections 2.1–2.2 and 4.2–4.8: redirect/code flow, replay, leakage, mix-up, injection, CSRF and PKCE downgrade; the remaining sections and browser/deployment gaps stay open. |
| [PAR and JWT client authentication](requirements-par-auth.md) | Applicable RFC 9126/7521/7523 client/assertion-producer clauses, optional features, AS/operator duties and focused evidence gaps. |
| [Sender constraints and resources](requirements-sender-constraints.md) | Direct RFC 8705/9449/8707 client duties, separating authentication, token binding, aliases, nonce/proof handling and audience signaling from AS/RS/operator enforcement. |
| [JWT and Message Signing](requirements-jwt-signing.md) | Final Message Signing client clauses, JAR, JARM and all 12 JWT BCP sections; unsupported optional features and specific regression gaps remain explicit. |

These are requirement accounts, not blanket compliance results. Finish the
remaining inherited-security and configuration/coverage work before declaring
SA04 complete.

This map describes the implementation at `8d2ec4d90e9645f546f2186f9bb6f0acd3fa2b6f`.
The follow-up mixed-key regression adds evidence without changing that runtime
implementation; its validation is recorded in the
[implementation plan](../../.github/protocol-quality-implementation-plan.md).
It links existing regression definitions, protocol collectors and recorded runs;
writing a row does not establish a new test result. The
[release review](release-review.md) records the refreshed suite and the complete
29-module Message Signing execution at `65fbdc8e49d70e85f99cbccc527428c91a785992`.
Earlier runs retain their recorded source and suite identities. The schema-4
[source check](source-identity.md) adds installation provenance for subsequent
runs; the complete source-qualified release matrix remains SA08 work.
The release review now also records a separate schema-4 hosted
Message Signing/sync result at `f9056d9b`, with all 29 modules and its
release-source check passed. Its source identity remains distinct from the
later namespace correction and other selections.

The package implements the OAuth client role. Applications and operators still
own their consent experience, issuer configuration, external callback routes,
TLS termination and credential custody. A successful simulated authorization
server (AS) or resource server (RS) condition does not establish those servers'
production behavior. No row establishes certification.

| Label | Concrete selection and settings |

| mTLS/OIDC | `fapi-mtls` and `fapi-mtls-auth`: 21 modules each, reference state, `fapi2` ID-token policy and the corresponding authentication/sender-constraint pairing. |

The [fixture](fixture-app.R) builds these settings through the public discovery
and client constructors. `id_token_profile = "fapi2"` changes the ID-token
algorithm policy only. It does not automatically enable PAR, confidential
authentication, sender constraint, the issuer-string assertion override or
browser-initiation controls. The [scope map](scope.md) retains per-selection
verdicts and fixture limitations.
